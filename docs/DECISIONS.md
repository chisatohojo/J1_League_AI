# Design Decisions

## 2026-09-16: クラブの永続IDを原表記から分離する

Decision: `data/master/teams.csv`をGit管理し、名称やprofile slugとは独立した`team_0001`形式のIDを割り当てる。
同一クラブのaliasはsource・source_name・任意の有効期間で解決し、IDは改称・昇降格・行の並べ替えで変更しない。
source_club_idには根拠照合用slugを保存するが、Eloの永続キーには使わない。

Reason: Data Siteの略称・全角半角・公式サイトの表示名が異なっても、長期間のクラブ同一性を維持するため。
取得原本・既存CSV・Validationは保持し、後続処理が必要な時だけコピーへhome_team_id / away_team_idを追加する。
未知名には明示的エラーを返す。IDの自動生成・名称の類似照合は行わない。

Names: canonical_nameは表示用の現在の登録名で、当時の名称は原データに保持する。
確認できたaliasだけ登録し、改称日が不明なら期間は空欄とする。
期間付きaliasは試合日を必須にし、同一source/nameの期間重複を拒否する。古い名称とIDは消去・再利用しない。
新クラブは原本と同一性を確認して未使用IDを手動追加する。旧sourceのslug変更でもIDを維持できる。

Status: 33クラブ・86 aliasを実装。全4,168試合・予定の8,336参照を一意に解決。
`616d345`までの更新基盤・69候補確認はcommit・push済みと確認した。
今回のマスターは未コミット。Elo本体・スタジアムマスターは対象外。
詳細は[チーム名称マスター仕様](TEAM_MASTER.md)を参照。

## 2026-09-15: 進行中2026/27 J1の更新境界と公式終了証拠

Decision: 取得ごとのraw/metadataと、解析・差分・結果のrevisionを不変で保存する。
同一snapshotの再処理は固定した比較基準・解析版から同一revisionを再利用し、検証成功後だけlatest参照を更新する。
前回取得と前回採用の比較を分け、欠落・訂正・解析版の変更を履歴として残す。

Reason: 進行中シーズンには予定表示310件・スコア掲載70件が共存し、予定変更と過去結果の訂正が起こり得る。
通常年度の全件完了検証は再利用せず、終了確認済みの部分集合だけを既存validate_matchesへ渡す必要がある。
`season=2026`と2027年開催日を保持し、既存Validationの仕様は維持する。

Identity: 公式ID付き結果はcompetition_key＋match_idを主キーにする。未開催行には公式IDがないため、
公式クラブprofile URLのslugから `j1_2026_2027:<home>:<away>` を作り、公式ID出現後に一意な対応を保存する。
日付を主キーにせず、延期で別試合を作らない。ID再割当や対戦方向変更の競合は自動統合しない。

Completion: 数値スコアや経過日だけでは終了確定としない。Data Site側の汎用終了フラグは確認できなかったため、
公式matchページの実 `section#game-over` の「試合終了」と左右得点を補助証拠に採用する。
canonical・通常J1大会・日付・節・左右クラブ・得点の一致を必須とし、script翻訳辞書やskeletonを除外する。
予定はscheduled、数値だけならcandidate、照合済みだけcompletedとする。初回は310/69/1。
確認済み結果とID・日付・節・得点が同じ場合だけ証拠を継承でき、変更時は新しい照合証拠を要求する。
終了0件の場合も正常として扱い、空DataFrameを拒否する既存Validationの条件を緩めない。

Publication: 正式な現在状態はlatest.jsonと不変revisionの組。トップ階層CSV等は閲覧用コピーとする。
通常例外ではコピーを復元し、強制終了後はreplayで復旧する。整合した複数ファイル読取はread_latestを使用する。
過去snapshot、rawの取得時刻、固定した採用基準を確認し、同じ入力や古い入力で最新状態を巻き戻さない。
各差分にbefore/after・snapshot・比較種別を含め、A→B→A訂正も失わない。欠落・未確認訂正は保留revisionへ保存する。

Status: 採用・実装・初回bootstrap検証済み。保存先は今回の指定どおり2026_27とし、旧調査原本2026_2027は保持。
2015～2025と百年構想リーグの36成果物は隔離再生成でも完全一致、既存Validationは変更なし。
詳細・未確認事項・受入テストは [更新設計報告](JLEAGUE_2026_27_UPDATE_DESIGN.md)を参照。

## 2026-09-15: 百年構想リーグを別大会とし、90分・単一試合・2戦全体の結果を分離する

Decision: `j1_hyakunen_2026`を通常J1とは別の大会キーにする。専用の原本解釈・正規化・大会検証と
オフラインCLIを追加し、既存の共通表読取を再利用する。2015～2025年の形式・共通CLI・Validationは変更しない。
`season=2026`とサイトの`source_year_id=20261`を区別する。

Reason: 地域180試合＋プレーオフ20試合は通年総当たりではない。さらに33017の一覧スコア2-1は延長込みで、
90分は0-0。既存の得点解釈や`full_season`へ割り当てると情報を誤る。

Model: `home_score`・`away_score`・`result`は90分のみ。延長の増分・PK得点・実施有無と決着方法を追加列にする。
地域のPKは単一試合の勝者を決め、POのPKは2戦全体の勝者を決める。
POの単一試合の勝者は90分＋延長の得点比較とし、PKによる対戦全体の勝者で上書きしない。
2戦全体の勝者は`playoff_ties.csv`にクラブ名と両match_id・確定日を保存する。
第2戦の勝者をカード勝者と混同せず、第1戦の行に将来の勝者を既知情報として埋め込まない。

Nullability: 地域はround1～18、POはleg1／2とする。適用外のround／leg・group・順位決定枠はnull。
延長／PK未実施の得点はnull、実施した0得点は0。必要な詳細が未確認なら成果物を生成せず停止する。
POのroundを正整数必須の旧CSVへ便宜的に合わせず、専用CSVと専用検証を使用する。

Validation: 地域の節・全方向対戦・クラブ別件数と、POの順位決定枠・正逆2戦・勝利数→得失点差→延長→PKを検証。
「PKありなら90分同点」は地域だけに適用する。POは第2戦が非同点でも2戦合計が同点ならPKに進み得る。
現存原本にPO PKはないため、人工fixtureでこのケースも確認する。抽選やみなし開催など未対応の決着は推測せず拒否する。

Status: 採用。通常2026/27 J1やElo・モデル処理には拡張しない。

## 2026-09-13: 期待件数を公式確認済みのクラブ数と総当たり回数から導出する

Decision: `SEASON_FORMATS` にクラブ数とstageごとの対戦回数だけを設定する。
2015/2016は18クラブ・各stage1回、2017は18クラブ・full_seasonで2回、2021は20クラブ・full_seasonで2回。
節数は `(N-1)×stage内対戦回数`、各節試合数は `N/2`、対戦組数は `N×(N-1)/2`、
年間試合数は対戦組数×年間対戦回数とする。`SEASON_STAGES` の節数もこの設定から導出する。
各クラブの年間/home/away件数、stage内の対戦網羅性も同じ構造を使用する。

Reason: 2021年の公式大会方式とHTMLは20クラブ・38節・380試合であり、18クラブ・306試合の固定前提は適用できない。
入力の件数やuniqueクラブ数を期待値にすると、欠落した入力自身に検証基準を合わせてしまう。
確認済み大会方式を期待値とし、実データはその期待値と照合する。奇数クラブ・変則対戦・別形式は未対応とし、
今回は確認済みの偶数クラブ・年間2回戦総当たり4年度だけを許可する。

Coverage: 各stage/roundで全クラブが1回ずつ出場することも確認する。
総件数・節別件数・年間出場数を維持したまま異なる節の試合を入れ替えると、従来は同節での重複出場を見逃せたため。
延期試合も開催日ではなく原本のstage/roundで集計し、実施日や節を補正しない。
この検証は大会構造の検査に置き、既存CSV Validation・必須10列・追加5列は変更しない。

Compatibility: 2021年の比較対象は確認済み2017年を明示し、`baseline_2017_sha256` を記録する。
2020年キャッシュを要求せず、未調査年を自動取得しない。2015～2017年のCSV・JSON・レビュー計8出力は
変更前とバイト単位で一致し、旧年度の形式・表示・名称・行列順を維持する。

Status: 採用。2021年380試合が既存Validation・CSV再読込・大会構造検証を通過。

## 2026-09-13: 2017年の1ステージ制をfull_seasonとして明示する

Decision: 公式大会方式と保存済みHTMLを確認し、`SEASON_STAGES` に検証済み年度のstageと節数を記録する。
2015/2016は1st・2nd各17節、2017はfull_seasonの34節とする。
2017年の大会原表記 `Ｊ１` はcompetitionに残し、roundを付け替えず1～34で保存する。
stageを欠損にせず `full_season` で通年リーグ戦を表す方針は、ユーザーの再開指示でも明示された。

Reason: 表の11列・日付・スコア・ID構造は共通だが、大会表記・ステージ内節数・対戦回数が異なる。
一律の2ステージ条件を緩めるのではなく、各年に合う大会表記と完全性を検証する必要がある。
18クラブ・306試合・各クラブ34/home17/away17という共通条件は維持し、stage内の153組は
2015/2016なら各1回、2017なら各2回を要求する。既存CSV Validationを変更しない。

Compatibility: 2015/2016年の固定期待値は更新せず、実出力5ファイルのバイト一致も確認する。
比較年度・レビュー表示のみ引数化し、2017年は2016年キャッシュと比較して `baseline_2016_sha256` を残す。
2018年以降やネットワーク取得器は対象外。大会・名前・行順の補正によるValidation通過は行わない。

Status: 採用。2017年306試合が既存Validationを通過し、全253件のpytest成功。

## 2026-09-13: 年度引数を持つ共通解析と従来出力の互換性を両立する

Decision: HTML解析・キャッシュ照合・シーズン集計を `src/collect/jleague.py` に集約する。
共通APIでは対象年を明示し、`scripts/inspect_jleague.py --year` が入出力を実行する。
旧年度別CLIと解析関数の既定値を互換入口に残す。2015年の集計JSONと2016年の比較・レビューは
既存の出力契約として維持し、共通CLI内で必要な年度分岐だけを残す。
対応は検証済み2015・2016年に限定し、既存Validation、15列、原本の名称・行順は変更しない。

Reason: 年度別スクリプト間の実装依存をなくし、解析の呼び出しにプロジェクトの配置や
CLIを必要としない構造にするため。年度形式の設定フレームワークやネットワーク取得は今回追加しない。
変更前コードで作成した人工データの期待出力と、退避した実データ出力の両方で完全一致を確認する。

Cache: 2016年と同じ厳格なmetadata照合を両年で使う。2015年旧CLIのmetadata任意は廃止し、
HTMLまたはmetadataが欠ける場合や来歴不一致の場合は停止する。来歴確認を省略して解析を進めたり、
自動再取得したりしない。取得済みの両年キャッシュはこの条件を満たす。

Status: 採用。データ源とCSV Validationの仕様変更なし。

## 2026-09-11: ステージ情報を追加列で保持し、既存CSV契約を維持する

Decision: `round` は各ステージ内の1～17を保持し、`stage` で1st / 2ndを区別する。
`match_id` はData Siteの `match_card_id` を使用する。大会名・節の原表記・キックオフ時刻・
試合詳細URLも追加列で保存する。チーム名・スタジアム名は取得表記を維持する。

Reason: 通年節番号への付け替えや独自ID生成による原本との対応喪失を避けるため。
既存Validationは追加列を保持するので、必須列や検証ロジックを変えずに2015年を扱える。
全角文字の構文解釈とクラブ・会場の名称統一は別処理にし、原本へ一括変換をかけない。

Status: 調査用正規化で採用。本番の名称マスターは未実装。

## 2026-09-11: 試合入力を検証済みDataFrameへ統一する

Decision: `load_matches` をCSVの読込窓口、`validate_matches` をDataFrame共通の検証・正規化窓口とする。
不正入力は `MatchValidationError(ValueError)` で通知し、入力原本の書き換え・行の除去・結果の自動修正を行わない。
追加列、行列順、indexを保持し、必須列のみ文字列・int64・datetime64[ns]へ統一する。

Reason: 取得元変更時に検証を再利用し、誤った結果を後続処理へ渡さず、取得原本との対応を保つため。
専用の抽象基底クラスや外部Validationライブラリは追加しない。
CSVは標準ライブラリの `csv.reader(strict=True)` で列数を確認してからDataFrame化する。
これにより先頭ゼロのIDを保持し、重複ヘッダーや列過多による暗黙のindex化・値の脱落を防ぐ。
数値はDecimal経由で整数性とint64の範囲を確認し、浮動小数点への変換による丸めを避ける。

Status: 採用

## 2026-09-11: Phase 1の日付・重複・欠損の境界を明示する

Decision: CSVの日付は仕様例の `YYYY-MM-DD`、DataFrameではdateとタイムゾーンなし午前0時の
datetime / Timestampも許容する。時刻を切り捨てず、日付以外の値は拒否する。
重複判定は空白除去後の `match_id` と `(season, match_date, home_team, away_team)` の2種類とする。
全必須列の欠損・空白を拒否し、seasonとroundは正、得点は非負、resultは得点との一致を要求する。

Reason: 月日順の推測や時刻情報の暗黙の喪失を避けるため。
異なるIDで同一試合が二重投入される場合も検出する一方、別日・別season・ホーム/アウェイが逆の対戦は許容する。
シーズンが暦年をまたぐケースを妨げないよう、seasonと日付年の一致や現在日以前という追加制約は置かない。
未開催試合の扱い・チーム名称統一は後続の入力仕様として検討し、今回先行実装しない。

Status: 採用

## 2026-09-11: Python 3.12と仮想環境を明示する

Decision: Python 3.12.14で `.venv` を作成し、実行時は仮想環境のPythonを直接指定する。
今回の端末は `.tools/bootstrap` にuv 0.12.13を導入し、uvの
`--install-dir .tools/python --no-bin --no-registry` でPythonをプロジェクト内に配置した。
初期依存は仕様の7ライブラリとpytestとし、直接依存と推移的依存をバージョン固定する。

Reason: 端末の既定Pythonは3.10.6。`py -0p` には3.12の登録があるものの実行ファイルがなく、
`py -3.12 -m venv .venv` が失敗したため、仕様で推奨される3.12をローカルに導入した。
既定環境やPowerShellのスクリプト実行ポリシーを変更せず、環境を再現できるようにするため。
uvとPython本体はGit対象外の `.tools/` に置き、アプリケーション依存と分けて管理する。
将来予定のSHAP・requests・Beautiful Soup・Streamlitは直接依存として追加しない
（Jupyter等が必要とする推移的依存はロックファイルに記録する）。

Status: 採用
