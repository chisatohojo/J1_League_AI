# J.League Data Site: 2015年J1の取得調査

調査日: 2026-09-11。今回の対象は2015年J1の1st / 2ndステージのみ。

2026-09-13追記: 解析実装は `src/collect/jleague.py` へ移動した。
`python -m scripts.inspect_jleague --year 2015` と従来の年度別コマンドが同じ処理を呼ぶ。
CSV・集計JSONは共通化前とバイト単位で一致。キャッシュはHTML・metadataの両方を必須とする。
現在の実行方法・APIは [README](../README.md) を参照。以下は取得調査時点の記録。

## 結論

[2015年J1の検索結果](https://data.j-league.or.jp/SFMS01/search?competition_frame_ids=1&competition_years=2015&tv_relay_station_name=)
へのGET 1回で、両ステージ計306試合のHTMLを取得できた。
試合日・節・ホーム・アウェイ・スコア・スタジアムと試合固有IDを一覧から抽出でき、
既存 `validate_matches` の変更なしで全306試合を受理できることを確認した。
個別の試合詳細ページやステージ別の結果ページは取得していない。

| 検証項目 | 1st | 2nd | 全体 |
| --- | --- | --- | --- |
| 試合数 | 153 | 153 | 306 |
| 開催日範囲 | 2015-03-07～06-27 | 2015-07-11～11-22 | 2015-03-07～11-22 |
| 節番号 | 1～17 | 1～17 | 各ステージの番号を保持 |
| 各節の試合数 | 9 | 9 | 34節分 |
| クラブ数 | 18 | 同じ18 | 18 |
| 各クラブの試合数 | 17 | 17 | ホーム17・アウェイ17 |

必須欠損、重複ID、既存契約での複合試合重複はすべて0件。
結果はホーム勝利118、引分75、アウェイ勝利113。総得点820、スタジアムは23表記。
各ステージに18クラブの全153組の対戦があり、年間のホーム・アウェイ付き306組も一意だった。
今回の結果にチャンピオンシップやカップ戦は含まれない。

## アクセス方法と回数

使用したURL:

```text
https://data.j-league.or.jp/SFMS01/search?competition_frame_ids=1&competition_years=2015&tv_relay_station_name=
```

| クエリ | 今回の値・意味 |
| --- | --- |
| `competition_years` | `2015`、対象年 |
| `competition_frame_ids` | `1`、J1リーグ |
| `competition_ids` | 未指定。今回の結果は1st / 2ndの両方を含む |
| `tv_relay_station_name` | 空。放送局による絞り込みなし |

HTTP 200、`Content-Type: text/html;charset=UTF-8`、386,173 bytes。
認証・Cookieの事前設定・JavaScript実行なしのPython標準ライブラリ `urllib.request` で取得できた。
HTML内の `$.repost` にも `/SFMS01/search` への `method="GET"` と検索条件の引き継ぎ処理がある。
試合行はサーバー側でHTMLに展開されており、今回の取得にブラウザ自動操作は不要。

ローカルからData Siteへの直接HTTPリクエストは**合計2回**。

1. `robots.txt`: 404。応答本体とmetadataを保存した。
2. 2015年J1検索結果: 200。全306試合を1回で取得した。

別途、公式Data Siteに対象を絞った検索エンジン照会を1回行い、URLを確認した。
CSS・JavaScript・画像、試合詳細306ページ、2016年以降の結果、追加のステージ別ページは取得していない。
以降の構造解析・正規化・検証は保存済みHTMLだけを再利用した。
`robots.txt` の404は利用・再配布の許諾を示すものではなく、公開・再配布条件は今回確認していない。

## HTML構造

対象は `table.table-base00.search-table` の1表。
`thead tr th` に11見出し、`tbody tr` に306試合があり、各行は11個の `td` を持つ。
別に検索条件の表があるため、ページ内の全tableを無条件に結合してはいけない。

| td位置（0始まり） | 見出し | 対応・扱い |
| --- | --- | --- |
| 0 | シーズン | `season` |
| 1 | 大会 | `competition`に原表記、`stage`に`1st` / `2nd` |
| 2 | 節 | `round`に節番号、`round_label`に原表記 |
| 3 | 試合日 | `match_date`へ日付変換 |
| 4 | K/O時刻 | `kickoff_time`に保持 |
| 5 | ホーム | `home_team`、セル内aの表示文字列 |
| 6 | スコア | `home_score` / `away_score`へ分割、aのhrefから`match_id` |
| 7 | アウェイ | `away_team`、セル内aの表示文字列 |
| 8 | スタジアム | `stadium`、表示されている略称を保持 |
| 9 | 入場者数 | 今回の入力に不要。原本に保存 |
| 10 | インターネット中継・TV放送 | 今回の入力に不要。日程変更注記も原本に保存 |

スコアのリンク例は `/SFMS02/?match_card_id=16804`。
詳細ページを開かずに試合IDとスコアの両方が得られる。
IDは連番とは限らないため、欠番を取得漏れの条件にしない。
HTML内には現在年のナビゲーションリンクもあるが、今回の解析対象は指定表の2015年の行のみ。

## 既存matches.csvへの正規化

- 必須10列の名前・型・result定義は変更しない。
- `match_id` は `match_card_id` の文字列。独自の節ベースのIDは生成しない。
- `15/04/29(水・祝)` などから月日を抽出し、シーズン年2015と表示年15の一致を確認して
  `2015-04-29` へ変換する。括弧内を曜日1文字に固定しない。
- `第１節第１日` の最初の整数を `round=1` にする。
  2ndを18～34節へ付け替えず、追加列 `stage` でステージを区別する。
- 節などの構文解釈にのみNFKCを使う。`Ｇ大阪`・`川崎Ｆ`などのチーム名や
  `ＢＭＷス`などのスタジアム名には適用せず、取得表記を保持する。
- `3-3` を整数の得点2列へ分割し、ホームが多ければ2、同点なら1、少なければ0を `result` にする。
- `competition`、`round_label`、`stage`、`kickoff_time`、`source_url`を追加列として保持する。
  現行Validatorは追加列を許容するため、変更は不要。
- 原本の行順を保持する。今回の一覧には隣接行の日付逆行は0件だったが、
  将来の処理で節番号順を時系列順の代わりに使わない。前倒し・延期により節番号と日付の順序は一致しない場合がある。

## オフライン再現

調査用スクリプトは2015年固定で、ネットワークアクセス機能を持たない。
保存済みHTMLから正規化候補を生成し、既存 `validate_matches` とCSV再読込の `load_matches` で検証する。

```powershell
.\.venv\Scripts\python.exe -m scripts.inspect_jleague_2015
```

出力先:

```text
data/processed/jleague/2015_matches_probe.csv
data/processed/jleague/2015_matches_probe.summary.json
```

原本のハッシュ、見出し・列数、2015年、対象ステージ、各ステージ153試合・17節・各節9試合・18クラブを検証する。
これは取得・正規化の成立性を調べるための出力であり、既定入力 `data/raw/matches.csv` は作成・上書きしない。

## 次の実装方針

1. 取得処理とHTML解析・正規化を分離したData Site用アダプターを作る。
   既存 `src/collect/matches.py` は共通の検証窓口としてそのまま使う。
2. 年・大会枠を明示した検索URLを使い、キャッシュとmetadataが存在し整合していれば通信しない。
   検索条件と原本ハッシュで来歴を追跡し、更新取得時は以前の原本を保持する。
3. 原本は `data/raw/jleague/`、正規化結果は `data/processed/` へ分離する。
   取得時はタイムアウトを設定し、HTTP失敗や想定外のHTMLを正常データとして扱わない。
4. ページ取得は逐次実行し、複数リクエストが必要な場合は間隔を設ける。
   2015年と同じ1ページ方式で足りるかを年ごとに確認し、無条件に詳細ページを巡回しない。
5. 本番化時は人工HTML fixtureで構造変更・対象年外・未知大会・不正スコア・重複・欠損をテストし、
   取得失敗を自動的な全件再取得で回復しないようにする。
6. チーム・スタジアム名称マスターを別途整備する。今回の略称を正式名称とみなして固定しない。

**今回の作業はこの調査報告まで。複数年取得には進んでいない。**
2016年以降の大会方式・検索結果の完全性、名称の年次変更、訂正データの更新方針は未検証。
2015年の試合数や2ステージ制を全年度へ一般化しない。
